01 · The Problem

The warehouse closes at 2 PM.
The showroom does not.

Seven hours of selling with no way to check what's in stock.

8 AM2 PM — warehouse closes9 PM — showroom closes
nobody can check stock
You can call and check stockSeven hours with no answer

No stock info after closing

Traders guess, or tell the customer to come back tomorrow. Phone calls and notebooks leave no record.

No proper way to order custom items

Local furniture can be made to order. But the request is only spoken, so it gets misheard or lost.

02 · Evidence

We measured the problem, we didn't guess it

Twelve traders surveyed.

83.4%

get customer requests after the warehouse closes often, or almost every day

75%

name not knowing what's in stock as their biggest problem with warehouses

66.7%

still have to make a phone call just to find out if an item is in stock

03 · The Solution

NALB — a private link between one warehouse
and its trusted traders

Not open to the public. The warehouse creates every account itself.

Stock you can see any time

Real quantities at any hour. Still works when the internet drops.

Custom orders, written down

The trader picks from what the workshop actually offers, and it is saved with the order.

Every order has a code

A unique code the trader reads back to the customer.

Trader mobile app
Flutter · Android & iOS
Admin dashboard
Laravel Blade · Tailwind CSS
Backend API
Laravel 13 · REST · SQLite
04 · Engineering Process

The Waterfall Model

The users were few and known, and the requirements did not change — so each phase was checked before the next one started.

1. Requirements

Interviews and a survey of retail traders

2. Design

UML diagrams, database design and screen mock-ups

3. Implementation

Laravel API, Blade dashboard, Flutter client

4. Testing

One documented test case per requirement

5. Deployment

Cloud server, released privately to the traders

The traders required a closed system — it was not my choice. That is why there is no sign-up page at all
05 · Project Boundaries

Scope and limitations

In scope

Mobile app (trader) — see stock, customise and order at any hour
Dashboard (admin) — products, stock, accounts and orders
Closed access — the warehouse creates every account

Out of scope

No delivery service — the buyer and seller arrange pickup themselves
No online payment — payment stays offline, the normal way in wholesale
06 · Implementation

Architecture and design patterns

Every part has one job — so a change happens in one place.

Backend (Laravel) — MVC with a service layer

MVC — each layer does one job
Service layer — one set of rules for the app and the dashboard
Middleware — a trader can't do admin work
Controller Service Eloquent Database

Mobile (Flutter) — Domain-Driven Design

Presentation — the screens
Application — app state (Riverpod)
Domain — the core objects
Data — talks to the server
Core — login, notifications, theme
